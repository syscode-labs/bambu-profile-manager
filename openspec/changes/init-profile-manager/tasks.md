## Post-launch feature: copy a filament profile to another printer, dependencies abstracted (2026-08-01)

User request after live-testing: pick a profile as it appears under printer A, pick a target printer, get it copied over with settings (vendor/name/color/print temps) intact — no manual target-parent list. Clarified via AskUserQuestion:
- Auto-match target parent by (same material root ancestor + printer token in name); ambiguous matches (2+) → stop and ask, never auto-pick.
- Target profile name: tool suggests `<source name> @<printer token>`, user confirms/edits before publish.
- No manual export/review-files step; instead every publish takes an automatic point-in-time backup with a restore action, in its own UI pane.

- [x] `internal/resolver.RootAncestorName` — walks to the top of a chain (material-family template), tested against the real fixture chain.
- [x] `internal/rebind.FindCandidateParents` — auto-search a target set by (root ancestor match + printer-token whole-word match via regex, avoids "P1S" matching "P1P"); returns all matches, feeds straight into the existing `Rebind`/`RebindAndPublish` candidate list. Tested: single real match, no match on wrong material, ambiguous returns both (synthetic decoy), end-to-end into `Rebind`.
- [x] `internal/backup` — `Take`/`List`/`Restore` point-in-time directory snapshots (non-recursive, skips `.staging`/`.backups`); `Restore` is non-destructive (overwrites, never deletes files added since). Tested including newest-first ordering and staging-dir exclusion.
- [x] `Service.BackupsDir` + auto-snapshot wired into `publishFlow` right before `Adapter.Publish`; `Service.ListBackups`/`RestoreBackup`. Tested end-to-end: publish takes a snapshot, unrelated live file mutated post-publish, restored back to pre-publish content, files added after the snapshot untouched.
- [x] CLI surface: `bambupm copy` (preview by default — shows match + suggested name, nothing published until `--confirm-name`; ambiguous matches list all candidates and refuse) and `bambupm backups list`/`restore`. `publish` also takes an automatic backup now (`--backups-dir`, defaults next to the db). Dry-run tested end-to-end against a throwaway copy of the real directory: preview, ambiguous-refusal, confirm+publish, backup list, corrupt-then-restore (confirmed non-destructive — left a post-snapshot file alone since it predates that snapshot).
- [x] Web UI pages: `/copy` (form → preview → confirm/publish), `/deployments/{id}` (detail + Check recognition button), `/backups` (list + Restore). `bambupm serve` takes `--user-dir`/`--system-dir`/`--backups-dir` to enable them. `internal/webui/copy_test.go` drives the full flow over real HTTP against real fixture data: preview → publish → simulate Studio save (`.info` write) → check-recognition → `ACTIVE`, plus backup/restore. Also smoke-tested with `serve` running against the real live directory (read-only: index, `/copy` lists real profiles, `/backups`).

## Extended feature: copy process (print) profiles across printers, 2026-08-01

User asked whether copying could extend to process/print profiles, not just filament. Researched against the real Bambu directory first (read-only) before building:

- **Process profiles don't follow filament's naming convention.** Filament gets one system leaf per exact printer model (`@BBL X1C`, `@BBL P1S`, ...), matched today by a printer-token regex against the profile name. Process profiles instead share one leaf across a whole printer family via an explicit `compatible_printers` field — confirmed there is no `@BBL P1S` process profile anywhere in the real system catalog at all; P1S reuses X1C's leaf, which lists both. A name-token match would report zero candidates even when a profile already applies.
- [x] `resolver.RootAncestorName` generalized from a hardcoded `fdm_filament_common` stop condition to "stop one level short of any ancestor whose name ends in `_common`" — confirmed against the real system catalog that this suffix, and only this suffix, marks a shared root for both filament (`fdm_filament_common`) and process (`fdm_process_common`, plus an extra `fdm_process_single_common`/`fdm_process_dual_common` layer process has and filament doesn't). Same function now serves both without duplication; existing filament tests unaffected (verified: no other `_common`-suffixed node exists anywhere in the real filament catalog).
- [x] `rebind.FindCandidateParentsByCompatiblePrinters` + `rebind.IsAlreadyCompatible` (`internal/rebind/candidates.go`) — the authoritative match for process profiles: resolves each same-family candidate's *effective* `compatible_printers` and checks membership, rather than name-token regex. `IsAlreadyCompatible` short-circuits the common real case: if the source profile already lists the target printer (inherited, not necessarily declared on the leaf itself), there's nothing to copy at all. Unit-tested against a synthetic fixture mirroring the real catalog shape (`TestIsAlreadyCompatibleInheritsFromParent`, `TestFindCandidateParentsByCompatiblePrintersMatchesRealCatalogShape`, `TestFindCandidateParentsByCompatiblePrintersNoMatch`).
- [x] `webui.Server` gained `ProcessSvc`/`ProcessUserDir`/`ProcessSystemDirs` and a `profileKind` bundle (`internal/webui/webui.go`) so the copy/preview/publish/deployment-detail/check/poller handlers serve both filament and process from the same code, parameterized rather than duplicated. Process gets its own db/Repo (`cmdServe` derives `<db>-process.db` automatically from `--process-user-dir`) so process and filament deployment IDs never collide. New routes: `/copy/process`, `/copy/process/preview`, `/copy/process/publish`, `/deployments/process/{id}`, `/deployments/process/{id}/check` — all 404 cleanly if `--process-user-dir` wasn't passed. `PollRecognition` now checks both kinds each tick.
