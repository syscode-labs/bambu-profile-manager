## Phase 3 — Bambu round trip (highest priority)
- [x] Agent F: Bambu adapter (discover/validate/stage/publish/observe/verify), atomic publish + backups — `internal/bambuadapter`. Publish refuses while Studio looks running (decisions.md #4, best-effort `pgrep` check, pluggable). All operations take an explicit root dir; tests use `t.TempDir()` only — **never write-tests against the real local BambuStudio directory**, since this is unattended and touches shared live state.
- [x] Agent F: reconciliation state machine (design.md §16) — `internal/reconcile`. `Advance` only permits table-defined transitions, so `ACTIVE` is unreachable without genuinely passing through `ROUND_TRIP_VERIFIED` (decisions.md #6, tested).
- [x] Agent F: `OBSERVED_BY_STUDIO` detector — `internal/reconcile.RewriteDetector` (infers from `.info` `updated_time`/`setting_id` change, decisions.md #5, **flagged unverified**, tested against the real `.info` fixture format) + `ManualDetector` fallback behind the same `ObservationDetector` interface.
- [x] Agent F: rollback — `Service.Rollback` finds the profile's most recent `ACTIVE` deployment, republishes its stored resolved profile through the same `publishFlow` (validate→stage→publish→observe→verify), and only counts as done once it independently re-reaches `ACTIVE` — never a bare file overwrite. Storage gap this surfaced and fixed: `RebindAndPublish` wasn't persisting a `ProfileVersion` for the rebound profile at all, so rollback had nothing to restore — added `DeploymentRepository` + version-on-publish, tested (`internal/service/service_test.go` `TestRollbackRepublishesLastKnownGoodRevision`).
- Exit gate: import → rebind → publish → Studio recognition → sync/reload → post-sync re-read → semantic equality. Do not begin broad UI work before this passes. **Real end-to-end publish against the live Bambu Studio directory needs the user present (Studio must be closed/reopened) and empirical validation of the OBSERVED_BY_STUDIO detector — cannot be completed unattended.**

## Post-launch feature: copy a filament profile to another printer, dependencies abstracted (2026-08-01)

User request after live-testing: pick a profile as it appears under printer A, pick a target printer, get it copied over with settings (vendor/name/color/print temps) intact — no manual target-parent list. Clarified via AskUserQuestion:
- Auto-match target parent by (same material root ancestor + printer token in name); ambiguous matches (2+) → stop and ask, never auto-pick.
- Target profile name: tool suggests `<source name> @<printer token>`, user confirms/edits before publish.
- No manual export/review-files step; instead every publish takes an automatic point-in-time backup with a restore action, in its own UI pane.

- [x] `internal/resolver.RootAncestorName` — walks to the top of a chain (material-family template), tested against the real fixture chain.
- [x] `internal/rebind.FindCandidateParents` — auto-search a target set by (root ancestor match + printer-token whole-word match via regex, avoids "P1S" matching "P1P"); returns all matches, feeds straight into the existing `Rebind`/`RebindAndPublish` candidate list. Tested: single real match, no match on wrong material, ambiguous returns both (synthetic decoy), end-to-end into `Rebind`.
- [x] `internal/backup` — `Take`/`List`/`Restore` point-in-time directory snapshots (non-recursive, skips `.staging`/`.backups`); `Restore` is non-destructive (overwrites, never deletes files added since). Tested including newest-first ordering and staging-dir exclusion.
- [x] `Service.BackupsDir` + auto-snapshot wired into `publishFlow` right before `Adapter.Publish`; `Service.ListBackups`/`RestoreBackup`. Tested end-to-end: publish takes a snapshot, unrelated live file mutated post-publish, restored back to pre-publish content, files added after the snapshot untouched.
- [x] CLI surface: `bambupm copy` (preview by default — shows match + suggested name, nothing published until `--confirm-name`; ambiguous matches list all candidates and refuse) and `bambupm backups list`/`restore`. `publish` also takes an automatic backup now (`--backups-dir`, defaults next to the db). Dry-run tested end-to-end against a throwaway copy of the real directory: preview, ambiguous-refusal, confirm+publish, backup list, corrupt-then-restore (confirmed non-destructive — left a post-snapshot file alone since it predates that snapshot).
- [x] Web UI pages: `/copy` (form → preview → confirm/publish), `/deployments/{id}` (detail + Check recognition button), `/backups` (list + Restore). `bambupm serve` takes `--user-dir`/`--system-dir`/`--backups-dir` to enable them. `internal/webui/copy_test.go` drives the full flow over real HTTP against real fixture data: preview → publish → simulate Studio save (`.info` write) → check-recognition → `ACTIVE`, plus backup/restore. Also smoke-tested with `serve` running against the real live directory (read-only: index, `/copy` lists real profiles, `/backups`).
- [x] `resolver.LoadDirs` extracted so CLI and web UI scan directories the same way (was duplicated, now one implementation).
- [x] Studio-running warning: `/copy`, the preview page, and `/backups` all show a callout if Bambu Studio looks open (same best-effort `pgrep` check `Publish` enforces; an unknown result also warns rather than staying silent, per decisions.md #4). A blocked publish renders a clear "Studio is open" page (422), not a raw error string. Confirmed against the real environment — Studio genuinely was open at test time, banner correctly fired.
- [x] **Visual restyle, 2026-08-01.** User called the bare `html/template` UI "horrible" and asked to brainstorm a real desktop app. Compared two throwaway POCs (Tailwind-in-browser vs. the same markup wrapped in Electron) — chose Tailwind-in-browser: stays a single Go binary, no Node/npm toolchain, matches the original "avoid Electron" call in design.md §6. All pages now go through one shared shell (`shell.go`: sidebar nav, header, warning-banner slot) with Tailwind (CDN) styling — cards, badges, timelines instead of bare lists. Architecture unchanged: still plain page reloads, still no client-side framework.
- [x] **Follow-up UI requests, 2026-08-01: timestamps, Bambu-Studio-style preview + compare, inline explanations, landing page.** Profile detail now shows a summary card (vendor/type/temps pulled from real field names, color swatch) instead of a raw JSON dump, plus revision timestamps (`ProfileVersion.CreatedAt` was already stored, just wasn't displayed). Landing page (`/`) rewritten from a bare profile list into an actual home page: one-paragraph explanation + 3 action cards, list below. Step-numbered inline explanations added to the copy flow, deployment detail, and backups pages.
- [x] **Second round, same day: settings grouped Bambu-Studio-style, compare across any profiles (not just revisions), up to 3, with highlighting.** All settings now bucket into heuristic categories (Basic/Temperature/Cooling/Flow & Retraction/Advanced — no authoritative field→tab map exists, documented as an approximation) instead of one flat table. Replaced the old same-profile-only 2-way diff with a generic `/compare?item=<profileID>:<revision>` (repeatable, 2-3 items): any profiles, any revisions, grouped like the settings view, differing rows highlighted (all rows shown, not just diffs — multi-item compare reads better that way than hide-identical). Caught and fixed a template scoping bug during testing: `$` in `html/template` always means the root data, not the enclosing range var — a nested `{{range .Values}}` referencing `$.Differ` silently meant the page-level struct, not the row, and 500'd until bound via `{{$row := .}}`.

**Bug found running `copy` against the real system profile directory (2026-08-01):** `RootAncestorName` walked all the way to the literal top of the inherits chain, landing on `fdm_filament_common` — a base EVERY material (ABS, PLA, PC, PETG, TPU) shares. First real run matched 22 unrelated-material profiles as "same family" for a P1S ABS copy. Fixed: stop one level short, at the material-specific template (e.g. `fdm_filament_abs`), confirmed against real system profiles that this generically distinguishes materials. Regression test added (`TestRootAncestorNameDistinguishesMaterials`).

## UI gaps found after shipping, same day
- [x] **Landing page only showed bambupm's own db-tracked profiles (1), not the user's real ~93.** Index now scans `--user-dir` live and lists everything, badging profiles with no db revision history as "not tracked"; those link to a new read-only `GET /live/{name}` view (resolves on the fly, no revisions/compare — those need a tracked ProfileVersion). Falls back to db-only listing if `--user-dir` isn't set (e.g. tests). Regression test: `TestIndexShowsUntrackedLiveProfiles`.
- [x] **"Target printer" was free text**, then **wrong data source.** First pass (`discoverPrinterTokens`) derived options from filament-profile naming, which meant real printer profiles the user actually has (e.g. custom "... - Obsidian HF" variants) never appeared — those live in the *machine* profile directory, a tree bambupm hadn't touched. Replaced with `discoverRealPrinters`: scans real machine profiles (`--machine-dir`, new `Server.MachineDirs`), resolves each one's inheritance chain to its authoritative `printer_model`/`nozzle_diameter` fields (confirmed real: system machine templates set `printer_model = "Bambu Lab X1 Carbon"` etc.), and maps that to the short code filament names actually use (`shortPrinterToken`, exceptions for X1 Carbon→X1C, A1 mini→A1M, H2D Pro→H2DP). Dropdown now shows the user's real printer names; confirmed against the live directory — all 3 "Obsidian HF" profiles appear, correctly resolved to `X1C 0.4`/`X1C 0.6`.
- [x] **Values displayed like Go's `fmt.Sprint`, not like Bambu Studio.** Underlying data was correct; the summary card / settings table / compare view rendered array-shaped fields (most numeric settings are stored one-entry-per-extruder, e.g. `nozzle_temperature: ["250","250"]`) as literal `[250 250]`. New `formatValue`: unwraps identical per-extruder values to one, joins genuinely distinct ones with " / ", and appends °C for temperature-named fields (name-based heuristic — no authoritative units schema exists). Applied everywhere a field renders (summary, grouped settings, compare, live view). Unit-tested.
- [x] **"Check recognition" button looked like it did nothing.** Working as designed — Studio hadn't been reopened+saved yet, so the check correctly found no change — but the redirect gave zero feedback, making a genuine no-op look identical to a broken click. Now redirects with `?checked=1` and shows an explicit "Checked just now — Studio hasn't picked it up yet" note when still `INSTALLED_LOCALLY`; a real internal error (as opposed to "not yet") is now also logged server-side instead of silently swallowed.
- [x] **Copy form: hover-preview button next to the profile selector.** An (i) button opens a popup showing the selected filament's summary + grouped settings (same data/formatting as the live profile view), fetched via a new `GET /api/profile-preview?name=...` HTML-fragment endpoint (`resolveLiveFields` shared with `/live/{name}`) and cached client-side per selection — vanilla JS, no framework. Tested (`TestProfilePreviewFragmentReturnsSummary`, `TestProfilePreviewFragmentNotFound`) and confirmed against the live directory.
- [x] **"Pick a parent" ambiguous-match text explained the wrong thing.** It named the choice without explaining what a "parent" is in Bambu Studio's data model. Text now states plainly that every filament profile inherits its settings from a base profile (that's how `@P1S`/`@X1C` variants share settings), and that N candidates matched material+printer so the tool won't guess.
- [x] **Real bug, caught live: a copy published to "X1" (a printer the user does not own) succeeded silently and never appeared in Bambu Studio.** `discoverRealPrinters` listed every Bambu-made model from the full system machine-profile catalog as a selectable target, not just the user's actual configured printers — nothing stopped picking a nonexistent one. First fix filtered to only `"from": "User"` profiles — too strict, user pushed back correctly: Studio lets you pick any nozzle size for a printer model you own without needing a customized "User" copy of that exact nozzle (unlike filament profiles). Corrected to model-level ownership: derive owned models from the user's own machine profiles, then include every nozzle variant (user *or* system stock) of an owned model. Confirmed against the live directory: X1C 0.2 (stock, never customized) now selectable since the user owns X1C in other nozzle sizes; X1/A1/H2D/etc. (models with zero owned variants) still correctly excluded. Regression tests: `TestDiscoverRealPrintersExcludesSystemTemplatesUserDoesNotOwn`, `TestDiscoverRealPrintersIncludesUnownedNozzleSizeForOwnedModel`. The bogus published file was deleted from the live directory after confirming Studio was closed.
